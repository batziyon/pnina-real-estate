## 1. OVERVIEW

### What Was Implemented

Slice 3 implements the **browser-to-storage direct upload** and **upload confirmation** flow for property images.

**Key capabilities:**

1. **Browser uploads directly to Vercel Blob storage** (bypasses Next.js server for binary data)
2. **Confirmation endpoint** persists metadata to database after successful upload
3. **Admin UI component** (`PropertyMediaUpload`) orchestrates the two-step flow
4. **PropertyForm integration** enables image upload in property creation/editing
5. **Idempotency** ensures retry-safe operations with server-controlled imageId

**Upload Flow:**

```
1. POST /api/admin/properties/[id]/images/generate-upload-url
   → Server generates: imageId, storageKey, presigned URL
   
2. Browser uploads binary directly to Vercel Blob
   → PUT <presignedUrl> with binary payload
   
3. POST /api/admin/properties/[id]/images/confirm
   → Server persists PropertyImage record with storageKey
```

## 2. ARCHITECTURE DECISIONS

### 2.1 Two-Step Upload Pattern

**Decision**: Separate upload intent generation from upload confirmation

**Rationale:**
- Vercel serverless functions have 4.5MB payload limit
- Binary data NEVER passes through Next.js server
- Server controls security-critical values (imageId, storageKey) before upload
- Confirmation step validates upload succeeded before persisting metadata

**Rejected Alternative**: Single-step upload through server
- Would hit Vercel payload limits for large images
- Increases server bandwidth costs
- Creates unnecessary bottleneck

### 2.2 imageId ≠ PropertyImage.id

**Decision**: Use separate `imageId` (UUID) during upload flow, distinct from Prisma auto-generated `PropertyImage.id`

**Rationale:**
- `imageId` generated in Step 1 (generate-upload-url), used as idempotency key
- `PropertyImage.id` generated by Prisma at DB insert (Step 3, confirm)
- Cannot use `PropertyImage.id` as upload flow identifier because it doesn't exist yet
- `(propertyId, imageId)` tuple serves as effective unique key for idempotency

**Key Implementation:**
```typescript
// Step 1: Generate imageId
const imageId = crypto.randomUUID();
const storageKey = `properties/${propertyId}/images/${imageId}.jpg`;

// Step 3: Confirm upload - check for existing record
const existing = await repository.findImageByStorageKey(propertyId, storageKey);
if (existing) {
  return existing; // Idempotent retry
}

// Insert new record (Prisma generates PropertyImage.id)
const image = await repository.addImage(propertyId, {
  url,
  storageKey,
  altText,
  isMain,
  sortOrder
});
```

**Why This Matters:**
- Client can safely retry confirmation if network fails
- Same `imageId` → same `storageKey` → same PropertyImage record
- No duplicate images in database

### 2.3 Main Image Logic

**Decision**: First image auto-set `isMain=true`, subsequent images `isMain=false`

**Rationale:**
- Every property needs a main image for listings
- Admin can change main image later via Slice 4
- Simple, predictable behavior for MVP

**Implementation:**
```typescript
const existingImages = await repository.getImages(propertyId);
const isMain = existingImages.length === 0;
```

**Known Limitation:**
- Concurrent uploads by multiple admins could create race condition
- Acceptable for MVP (admin UI, single user expected)
- No transaction locking implemented

**Deferred to Slice 4:**
- Unique constraint on `isMain=true`
- Optimistic locking for concurrent operations

### 2.4 sortOrder Calculation

**Decision**: `sortOrder = max(existing.sortOrder) + 1`, or `0` if no images

**Rationale:**
- Handles deletions correctly (doesn't rely on count)
- Preserves gaps in sort sequence
- Simple, deterministic

**Implementation:**
```typescript
const sortOrder = existingImages.length === 0
  ? 0
  : Math.max(...existingImages.map(img => img.sortOrder)) + 1;
```

**Example:**
```
Initial state: []
Upload image A → sortOrder=0, isMain=true

State: [A:0]
Upload image B → sortOrder=1, isMain=false

State: [A:0, B:1]
Delete A

State: [B:1]
Upload image C → sortOrder=2, isMain=false
```

## 7. IDEMPOTENCY DEEP DIVE

### Problem Statement

Network failures during Step 3 (confirm) create ambiguity:
- Did the database insert succeed before connection dropped?
- Should client retry or will retry create duplicate?

### Solution Design

**Effective Unique Key**: `(propertyId, storageKey)`

**Why Not PropertyImage.id?**
- `PropertyImage.id` is Prisma auto-generated at DB insert (Step 3)
- Cannot use it as idempotency key because it doesn't exist during Step 1
- `imageId` generated in Step 1 is used to construct `storageKey`
- `storageKey` becomes the stable identifier across retry attempts

**Implementation Flow:**

```typescript
// Step 1: Generate Upload Intent
const imageId = crypto.randomUUID();
const storageKey = `properties/${propertyId}/images/${imageId}.jpg`;
// → Client receives: { imageId, storageKey, presignedUrl }

// Step 3: Confirm Upload (with retry safety)
const existing = await repository.findImageByStorageKey(propertyId, storageKey);
if (existing) {
  return existing;  // ← Idempotent: return existing record
}

// Only insert if not exists
const image = await repository.addImage(propertyId, {
  url,
  storageKey,  // ← Unique per imageId
  altText,
  isMain,
  sortOrder
});
```

### Retry Scenarios

**Scenario 1: Network failure before DB insert**
```
1. Client calls /confirm
2. Network drops before DB insert
3. Client retries with same payload
4. findImageByStorageKey() returns null
5. New record inserted → Success
```

**Scenario 2: Network failure after DB insert**
```
1. Client calls /confirm
2. DB insert succeeds → PropertyImage created
3. Network drops before response reaches client
4. Client retries with same payload
5. findImageByStorageKey() returns existing record
6. Existing record returned → Success (no duplicate)
```

**Scenario 3: Malicious retry with different metadata**
```
1. First request: { imageId: "abc", altText: "House" }
2. Record inserted successfully
3. Second request: { imageId: "abc", altText: "Hacked" }
4. findImageByStorageKey() returns existing record
5. Existing record returned (altText="House" preserved)
6. Malicious altText rejected implicitly
```

### Edge Cases

**Q: What if user generates new upload URL with same imageId?**
**A**: Impossible — `crypto.randomUUID()` collision probability is negligible

**Q: What if storageKey is reused across properties?**
**A**: Prevented by `propertyId` in path: `properties/${propertyId}/images/...`

**Q: What if admin deletes image then uploads with same imageId?**
**A**: Won't happen — deletion removes DB record but storageKey check fails (blob still exists)

### Database Constraints

**No unique index on `storageKey`** in Slice 3:
- Repository-level idempotency check sufficient for MVP
- Slice 4 may add unique constraint for database-level enforcement

**Why This Works:**
- Single-threaded admin operations (no concurrent uploads expected)
- Race condition window is milliseconds (DB insert time)
- Worst case: duplicate record with same storageKey (detectable via admin UI)

### Component: PropertyMediaUpload

**File**: `src/components/admin/PropertyMediaUpload.tsx`

**Responsibilities:**

**State Management:**

```typescript
const [uploading, setUploading] = useState(false);
const [error, setError] = useState<string | null>(null);
const [progress, setProgress] = useState<string>('');
```

**Upload Flow Implementation:**

```typescript
async function handleFileChange(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  if (!file) return;

  setUploading(true);
  setError(null);
  setProgress('Generating upload URL...');

  try {
    // Step 1: Generate upload intent
    const intentRes = await fetch(`/api/admin/properties/${propertyId}/images/generate-upload-url`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ filename: file.name, contentType: file.type }),
    });
    
    if (!intentRes.ok) throw new Error('Failed to generate upload URL');
    
    const { imageId, storageKey, presignedUrl } = await intentRes.json();

    // Step 2: Upload binary directly to Vercel Blob
    setProgress('Uploading to storage...');
    const uploadRes = await fetch(presignedUrl, {
      method: 'PUT',
      body: file,
      headers: { 'Content-Type': file.type },
    });

    if (!uploadRes.ok) throw new Error('Failed to upload to storage');

    const { url } = await uploadRes.json();

    // Step 3: Confirm upload
    setProgress('Confirming upload...');
    const confirmRes = await fetch(`/api/admin/properties/${propertyId}/images/confirm`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ imageId, url, storageKey }),
    });

    if (!confirmRes.ok) throw new Error('Failed to confirm upload');

    const image = await confirmRes.json();
    onUploadComplete(image);
    setProgress('Upload complete!');
    
  } catch (err) {
    setError(err instanceof Error ? err.message : 'Upload failed');
  } finally {
    setUploading(false);
  }
}
```

**UI Elements:**

```tsx
<div className="border-2 border-dashed border-gray-300 rounded p-6">
  <input
    type="file"
    accept="image/*"
    onChange={handleFileChange}
    disabled={uploading}
    className="block w-full"
  />
  
  {uploading && <p className="mt-2 text-sm text-gray-600">{progress}</p>}
  {error && <p className="mt-2 text-sm text-red-600">{error}</p>}
</div>
```

**Features:**
- Disabled state during upload prevents duplicate uploads
- Progress messages shown at each step
- Errors displayed inline
- File input accepts `image/*` only

## 10. KNOWN ISSUES & LIMITATIONS

### 10.1 Concurrent Upload Race Condition

**Issue**: Multiple admins uploading images simultaneously could result in multiple images marked `isMain=true`

**Scope**: Main image calculation is not transactionally locked

**Code:**
```typescript
const existingImages = await repository.getImages(propertyId);
const isMain = existingImages.length === 0;  // ← Race condition window
```

**Scenario:**
```
Time 0: Admin A calls confirm → existingImages.length = 0 → isMain = true
Time 1: Admin B calls confirm → existingImages.length = 0 → isMain = true
Time 2: Both records inserted with isMain=true
```

**Mitigation:**
- Expected usage: Single admin per property
- Window is milliseconds (DB query to insert)
- Slice 4 can add unique constraint on `(propertyId, isMain=true)`

**Status**: Accepted limitation for MVP

### 10.2 Storage Key Validation

**Issue**: Server trusts client-provided `storageKey` in confirm request

**Risk**: Malicious client could provide arbitrary `storageKey`

**Current Validation:**
```typescript
ConfirmImageUploadSchema = z.object({
  storageKey: z.string().min(1),  // ← Only checks non-empty
});
```

**Mitigation Options:**
1. Add pattern validation: `z.string().regex(/^properties\/[\w-]+\/images\/[\w-]+\.\w+$/)`
2. Server-side lookup: Re-fetch upload intent record by imageId
3. JWT signing: Sign storageKey in Step 1, verify in Step 3

**Status**: Deferred to security audit

### 10.3 No Image Deletion in UI

**Issue**: Uploaded images cannot be deleted via UI

**Workaround**: Database deletion or wait for Slice 4

**Status**: By design — Slice 4 scope

### 10.4 No Main Image Override

**Issue**: Cannot change which image is main after upload

**Workaround**: Database update or wait for Slice 4

**Status**: By design — Slice 4 scope

### 10.5 No Image Reordering

**Issue**: Cannot change sortOrder after upload

**Workaround**: Database update or wait for Slice 4

**Status**: By design — Slice 4 scope
