## 1. IDENTITY MODEL

### Current Implementation

**Two distinct identifiers exist:**

1. **`imageId`** (CUID)
   - Generated in `GenerateImageUploadUseCase` via `createId()`
   - Used to construct `storageKey`: `properties/{propertyId}/images/{imageId}.{ext}`
   - **NOT persisted in database**
   - Exists only during the upload flow (Step 1 → Step 2 → Step 3)

2. **`PropertyImage.id`** (CUID from Prisma)
   - Auto-generated by Prisma during `addImage()` call
   - Schema: `id String @id @default(cuid())`
   - Persisted in database
   - **Unrelated to upload flow `imageId`**

### Critical Finding

**The `imageId` used during upload is NOT stored anywhere.**

```typescript
// generate-image-upload.use-case.ts (Step 1)
const imageId = createId();  // ← Generated
const storageKey = generateImageStorageKey(propertyId, imageId, extension);
// imageId returned to client but NOT saved

// confirm-image-upload.use-case.ts (Step 3)
const existingImage = existingImages.find((img) => img.id === input.imageId);
// ← WRONG: Comparing upload flow imageId to PropertyImage.id
```

**This is a fundamental identity confusion bug.**

## 2. IDEMPOTENCY — 🚨 BROKEN

### The Idempotency Check

**Location**: `confirm-image-upload.use-case.ts:65-70`

```typescript
// 4. Check for idempotency: if image already exists with this imageId, return it
const existingImages = await this.propertyRepository.findImages(propertyId);
const existingImage = existingImages.find((img) => img.id === input.imageId);
if (existingImage) {
  // Image already confirmed - return existing record (idempotent)
  return existingImage;
}
```

### Why This Is Broken

**`input.imageId` is the upload flow identifier (from Step 1).**  
**`img.id` is the Prisma auto-generated database ID (from Step 3 insert).**  

**These are completely different values.**

The idempotency check will **NEVER** match because:
- `input.imageId` = `"cm3x2def"` (from generate-upload-url)
- `img.id` = `"cm3x9xyz"` (from Prisma insert)

### Consequence

**Retrying confirmation WILL create duplicate database rows:**

```
Scenario:
1. Generate upload intent → imageId = "abc123"
2. Upload succeeds
3. Confirm upload → Prisma creates PropertyImage with id = "xyz789"
4. Network drops before response reaches client
5. Client retries with imageId = "abc123"
6. existingImages.find(img => img.id === "abc123") returns undefined
7. New PropertyImage created with id = "def456"
8. Result: TWO PropertyImage records for the same blob
```

### Verification

**The current code is NOT idempotent.**  
**This is a BLOCKER.**

## 4. EXISTING PROPERTYIMAGE ID

### Should We Use imageId as PropertyImage.id?

**Current Schema:**
```prisma
model PropertyImage {
  id String @id @default(cuid())  // ← Prisma auto-generates
}
```

**Alternative:**
```prisma
model PropertyImage {
  id String @id  // ← Client provides (from upload intent)

```

### Analysis

**Advantages of using upload flow `imageId` as `PropertyImage.id`:**
1. ✅ Single source of truth for identity
2. ✅ Idempotency becomes trivial (Prisma unique constraint enforces it)
3. ✅ No identity confusion
4. ✅ Client can reference image by known ID immediately

**Implementation:**
```typescript
// Step 1: Generate upload intent
const imageId = createId();  // This WILL BE the PropertyImage.id

// Step 3: Confirm upload
const image = await prisma.propertyImage.create({
  data: {
    id: input.imageId,  // ← Use client-provided ID
    propertyId,
    storageKey,
    // ...
  }
});
// If duplicate: Prisma throws unique constraint error → catch → return existing
```

**This is the simplest correct identity model.**

### Prisma Schema Change Required

```prisma
model PropertyImage {
  id         String   @id  // Remove @default(cuid())
  propertyId String
  storageKey String   @unique  // Add unique constraint
  // ...
```

## 5. CONCURRENT CONFIRMATION

### Scenario: Two Identical Requests Arrive Simultaneously

```
Timeline:
T0: Request A calls findImages() → 0 images found
T1: Request B calls findImages() → 0 images found
T2: Request A calls addImage() → inserts PropertyImage (id=xyz1)
T3: Request B calls addImage() → inserts PropertyImage (id=xyz2)
Result: TWO PropertyImage records with SAME storageKey
```

### Can This Happen?

**YES, absolutely.**

The current implementation has **NO** concurrency protection:
- No database transactions
- No unique constraints
- No optimistic locking
- Window is milliseconds but real

### Actual Code

**`confirm-image-upload.use-case.ts`:**
```typescript
const existingImages = await this.propertyRepository.findImages(propertyId);
// ← Race condition window starts here

const existingImage = existingImages.find((img) => img.id === input.imageId);
// ← Even if this worked, still a race

// ... 50 lines of validation ...

const image = await this.propertyRepository.addImage(propertyId, { /* ... */ });
// ← Race condition window ends here (insert completes)
```

**Time between read and write: ~10-50ms depending on validation.**

### First Image / Main Image Behavior

**Code:**
```typescript
const isMain = existingImages.length === 0;
```

**With concurrent first confirmations:**
```
T0: Request A: existingImages.length = 0 → isMain = true
T1: Request B: existingImages.length = 0 → isMain = true
T2: Both insert with isMain = true
Result: TWO images marked as main
```

**This is a correctness violation.**

## 7. STORAGE CLEANUP

### Scenario: Upload Succeeds, Confirmation Fails

```
Flow:
1. Generate upload intent → imageId, storageKey, presignedUrl
2. Browser uploads to Vercel Blob → SUCCESS (blob exists)
3. Client calls /confirm → FAILS (network error, validation error, etc.)
Result: Blob exists in storage, NO PropertyImage record in database
```

### What Happens?

**Storage orphan is created.**

### Current Behavior

**NO cleanup implemented.**

The blob remains in Vercel Blob indefinitely:
- Consumes storage
- Incurs cost
- Unreferenced (no database record)

### Is This a Blocker?

**No, but suboptimal.**

**Reasons it's NOT a blocker:**
1. Upload presigned URLs expire (typically 1-2 hours)
2. Failed confirmations are rare (user will retry)
3. Orphans are invisible to users (not in database)
4. Can be cleaned up by background job (future work)

**Reasons it's SUBOPTIMAL:**
1. Storage costs accumulate
2. No automatic cleanup mechanism
3. Abandoned uploads waste resources

**Recommendation:** Add background job to delete blobs without PropertyImage records older than 24 hours.

**Status:** Acceptable for MVP, should fix in post-launch optimization.

**Schema migration:**
```prisma

```

**Use case change:**
```typescript
// confirm-image-upload.use-case.ts

// OLD (broken):

// NEW (correct):

  const image = await this.propertyRepository.addImage(propertyId, {
    id: input.imageId,  // ← Use upload flow ID

  if (error.code === 'P2002') {  // Prisma unique constraint violation

    return existing;
  }
  throw error;
}
```

**Repository change:**
```typescript
// prisma-property.repository.ts

async addImage(
  propertyId: string,
  data: Omit<PropertyImageData, "propertyId" | "createdAt"> & { id: string }

    data: {
      id: data.id,  // ← Client-provided ID
      propertyId,
      storageKey: data.storageKey,
      // ...
    },
  });
  return toImageData(record);
}

async findImageById(imageId: string): Promise<PropertyImageData | null> {
  const record = await prisma.propertyImage.findUnique({
    where: { id: imageId },
  });
  return record ? toImageData(record) : null;
}
```
